# 13 · 多策略并排与「把历史交给策略」

> 对应沙盒页新增的两种用法：
> **多策略对比模式**（同一条秘密下多个策略各自推进、并排看）
> 与**策略接管**（手动试玩时把当前历史交给任意策略，让它预测下一步）。
> 相关代码：`templates/index.html`、`static/js/sandbox.js`、`web/api.py`
> （`MultiGameSession`、`POST /api/advise`、`POST /api/games` 的 `mode="multi"`）。

## 1. 多策略对比（`mode = "multi"`）

### 为什么这样设计

单策略模式只能看到“一个策略的一局”；要判断“哪个策略更好”，
唯一公平的做法是**让它们面对同一条秘密**——否则差异可能只是题目难度不同。
这正是 `engine/simulator.run_benchmark` 的配对设计，本模式把它搬到了界面上，可交互、可单步。

### 用法

1. 模式选「多策略对比」；
2. 在「参与对比的策略」里增删策略、改参数（最多 6 个，重复 key + 不同参数也算不同变体）；
3. 点「开新局」→ 所有策略拿到**同一条秘密**，第 0 轮；
4. 三种推进方式：
   * 「所有策略各走一步」——每点一次，所有策略各推进 1 轮；
   * 「只让这个策略走一步」——单个策略单独推进（用来观察“谁先收敛”）；
   * 「自动跑完」——各自跑到解出或到轮次上限。
5. 每张卡片里有：**本轮猜测**（带逐位反馈颜色）、**候选组合矩阵**（10×10，着色累积）、
   **对局历史**、以及「第 n 轮：为什么这么选」的折叠面板（逐位理由）。
6. 勾「显示秘密」可在跑完后核对——所有卡片显示的秘密必然相同。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/games` | `{"mode": "multi", "seed": 7, "maxRounds": 40, "plan": [{"key": "two_phase", "params": {…}}, …]}` |
| POST | `/api/games/<gid>/step` | 空 body = 全部各走一步；`{"only": 1}` = 只走第 2 个 |
| POST | `/api/games/<gid>/play` | 跑到全部结束，返回每个策略的 `{index, gameId, solved, rounds}` |
| GET | `/api/games/<gid>` | `{gameId, mode: "multi", entries: [...]}`，每个 entry 字段与单策略一致 |

`gameId` 形如 `multi-<hex>`；每个 entry 内部仍是标准 `SequenceGame.state()`，
并额外把**每轮的决策解释**并进 `history[i].decision`。

## 2. 把历史交给策略（`POST /api/advise`）

### 场景

手动试玩到一半，想看看“如果换成某个策略，它会怎么下”。
界面上的入口是工具条里的「把当前历史交给策略」：选策略（可调参数）→「让策略预测下一步」，
然后 10 个槽位会被该策略的猜测填满，并弹出逐位理由；**仍然可以手动改**再点「提交猜测」。

### 关键实现：忠实重放

策略内部有状态（`used` 计数、信念、以及随机数流）。只把整段历史一次性喂给策略，
会得到和“真实对局”不同的平局选择（随机数消耗次数不同）。
所以服务端**按历史逐步重放**：

```python
strategy = create(key, seed=seed, **params)
for step in range(len(history)):
    strategy.next_guess(history[:step])      # 重放，保证 RNG 与计数走到同一状态
guess = strategy.next_guess(history)          # 这一次才是“它真会下的那步”
```

这样 ``/api/advise`` 的结果与“同一个 seed 从第一轮开始玩到该处”**逐位一致**
（`tests/test_explain_and_multi.py: test_history_replay_matches_direct_replay` 守这条）。

请求 / 响应：

```jsonc
// POST /api/advise
{
  "strategy": "position_entropy",
  "params": {"pick_mode": "split"},
  "seed": 5,                    // 可选；给定时结果可复现
  "explain": true,              // 默认 true，附带逐位理由
  "history": [                  // 也接受 [[guess, feedback], …] 形式
    {"guess": [[1,1], …], "letters": "MWMWWMPWMW"},        // 字母或
    {"guess": [[1,1], …], "feedback": ["MISPLACED", …]}    // 完整名都行
  ]
}
// → {"strategy", "strategyName", "rounds", "guess": [[a,b]…], "decision": {…}}
```

服务端**不需要知道秘密**：只拿历史重放信念，
所以这个接口也能用来分析“人工逐步猜测”里保存的对局。

## 3. 实现要点与取舍

* 解释只读、不参与决策，因此**并排对比仍然公平**：打开解释不会改变任何一步下法
  （`two_phase` 的均值仍是 6.125 轮，五个策略的均值与插桩前逐位一致）。
* 多策略会话共享一个 `gameId`（`multi-…`）；每个子对局仍有自己的 id，日志与存档互不干扰。
* 每轮解释会随对局历史一起返回（`history[i].decision`），前端因此可以“想看点哪个就点哪个”，
  不需要为解释单独建接口。
* 手动模式提交的那一轮没有解释（是人写的猜测），字段为 `null`——界面会显示“无解释数据”。
* 上限：一次最多对比 6 个策略（前端限制）/ 24 个变体（后端 `MAX_STRATEGIES_PER_RUN*2`）。
