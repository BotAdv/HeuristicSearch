## 第 1 轮 · 需求提交（用户提示词原文）

> python环境 conda activate  flask_env
>
> 我们正在研究一个“组合猜序列”游戏，需要你用 Flask + 前端搭建一个可扩展的沙盒环境，用于验证不同启发式搜索策略的性能。
>
> **【游戏规则】**
> 1. 对象集合 U = {1,2,...,10}。
> 2. 一个“组合”是从 U 中允许重复地选两个对象，不计顺序，表示为 (a,b)，1 <= a <= b <= 10。
> 3. 全部组合共 C(11,2) = 55 个，包含 10 个自组合 (1,1),(2,2),...,(10,10)。
> 4. 本游戏预先删除以下 10 个组合，玩家已知它们不可用：(1,5), (2,4), (3,7), (4,6), (5,6), (6,8), (7,10), (8,9), (8,10), (9,10)。因此实际候选组合集合 S 共 45 个。
> 5. 秘密序列 x = (x_1,...,x_10) 是长度 10 的序列，每个 x_i 从 S 中选取，允许重复。
> 6. 玩家每轮提交一个猜测序列 g = (g_1,...,g_10)，每个 g_i 从 S 中选取。
> 7. 对每个位置 i，反馈按以下优先级判定，高优先级覆盖低优先级：
>    (1) 完全正确：g_i == x_i
>    (2) 正确但位置错误：g_i != x_i，但存在 j != i 使得 g_i == x_j
>    (3) 部分正确：g_i != x_i，且 g_i 不在其他任何位置出现，但 g_i 与 x_i 至少共享一个元素
>    (4) 完全错误：以上都不满足
> 8. 当所有 10 个位置都返回“完全正确”时，游戏结束。
>
> **【重要】**
> - “正确但位置错误”会掩盖当前位置的真实信息，玩家无法从该位置本次反馈中得知 g_i 与 x_i 的关系。
> - 反馈是一个长度为 10 的向量，每个元素取值为 {CORRECT, MISPLACED, PARTIAL, WRONG}。
>
> **【需要验证的核心问题】**
> 1. 不同启发式策略在期望步数上的表现差异。
> 2. 是否存在比“先确定组合集合，再确定顺序”更优的混合策略。
> 3. “正确但位置错误”反馈对最坏和期望步数的影响。
> 4. 动态自适应策略与固定策略、贪心策略的对比。
>
> **【评估指标】** 平均步数（期望）、中位数步数、90 分位数、99 分位数、最坏步数、每轮信息增益（可选）、计算耗时
>
> **【策略接口】** 每个策略实现为一个类，提供方法：
> ```python
> def next_guess(self, history) -> List[Tuple[int,int]]
> ```
> 其中 history 是之前所有轮次的 (guess, feedback) 列表。策略内部可以维护自己的信念状态。
>
> //pass：记录项目过程中的所有交互信息，包括提示词、每轮反馈，将其存入根目录下的Doc文件，按照功能和任务类型进行记录，新功能则新建一个文件，对功能的修改则记录在对应功能对应说明文件中；

**处理反馈（第 1 轮）**

* 确认环境：`flask_env` = Python 3.10.20 / Flask 3.1.3 / numpy 2.2.6（无 pandas、无 scipy，
  统计部分改用标准库 `math` 手写）。
* 工作区为空目录，从零搭建；确定分层：`core`（纯规则）→ `strategies`（可插拔）→
  `engine`（实验）→ `web/templates/static`（展示）。

## 第 2 轮 · 核心规则层与单元测试

**新增文件**：`core/game.py`、`core/sequence_game.py`、`config.py`、`tests/test_game.py`

**处理反馈**

* `core/game.py` 用模块级 `assert` 锁定 55 / 45 这两个基数，把规则常量集中在一处；
* `evaluate()` 严格按优先级实现，`counts[g] > 0` 这一判断同时覆盖了
  “g_i 出现在其它位置”，避免用 `j != i` 循环造成性能损失；
* 写了 14 个规则用例，覆盖优先级、PARTIAL 的“独苗”前提、长度校验、可复现性。

**遇到的坑（第 1 个）**

* 用例 `test_partial_requires_unique_value` 首次运行失败。
  原因是**我的用例写错了**：设 $x=(1,2)^{10}$、$g=(1,3)^{10}$ 时，
  $(1,3)$ 并不在支持集中，所以正确判定是 `PARTIAL`（共享元素 1），不是 `MISPLACED`。
* 修正为：$x=((1,2),(3,3),(1,2),(4,4)^7)$、$g=((3,3),(1,2),(3,3),(4,4)^7)$，
  此时三个位置都因“组合在别处出现”判 `M`，且全序列不含 `P`。
* **教训**：`M` 与 `P` 的分界是“**该组合是否属于支持集**”，不是“是否与 $x_i$ 共享元素”。
  这条后来成了所有策略里最有价值的剪枝依据。

**结果**：23 个测试全部通过。

## 第 3 轮 · 策略层（7 个策略）

**新增文件**：`strategies/base.py`、`belief.py`、`random_strategy.py`、`fixed_cycle.py`、
`naive_position.py`、`two_phase.py`、`position_entropy.py`、`adaptive_hybrid.py`、
`particle_entropy.py`、`__init__.py`

**处理反馈**

* `Strategy` 基类提供 `_sync(history)`，只把**尚未吸收**的轮次交给 `observe()`，
  既能增量维护状态，也能在外部重置 history 时自动重建，避免策略状态与 history 不一致。
* 把易错的推理抽到共享的 `belief.py`：
  `PositionBelief`（逐位置候选集合 + 四条推理 + global_prune）与 `SupportTracker`（支持集/重数）。
* `particle_entropy` 是本项目唯一需要重计算的部分，用 NumPy 把反馈判定写成
  `evaluate_particles()`（一次算完所有粒子），单候选评分 $O(P\cdot10)$；
  粒子重采样从“逐位置候选集合的乘积分布”提议，保证真解一定在提议分布支持内。
* `SupportTracker.observe()` 里加入常数序列自动识别，使 `two_phase` 的重数探针
  只需发一个 `(c,…,c)` 就能读出精确重数。

## 第 6 轮 · 第一次基准实验：结果与预期不符

**发现**：预期“粒子滤波 + 全局最大熵”最强，实测它并不占优：

| 策略 | 平均步数 |
| --- | --- |
| 自适应混合 | 7.973 |
| 粒子滤波 + 全局最大熵 | 8.047 |
| 逐位置信息熵贪心（entropy 准则） | 8.107 |
| 朴素位置独立贪心 | 9.023 |
| 两阶段（exact） | 12.830 |

**处理反馈**

1. 先怀疑是评分目标选得不好，给 `particle_entropy` 加了 `objective` 参数
   （entropy / entropy_correct / expected_remaining / expected_correct）做消融；
2. 结果四种目标两两比较 p 值全部 > 0.19，**没有显著差异** —— 排除“目标函数”这一解释；
3. 转向消融参数，运行 `naive_position[global_prune=True]`，得到 **6.930** 轮，
   比当时所有策略都快 → 说明真正的关键不在“更复杂的建模”，而在更基本的剪枝与取值准则。

## 第 7 轮 · 定位差异：轮内重复组合

**异常**：`naive_position[global_prune=True]` 6.930，而
`position_entropy[pick_mode=least_used, global_prune=True]` 7.500 —— 两者“看起来是同一个算法”。

**定位过程**

* 逐行比对两处取值代码，发现唯一实质差异：`naive_position._pick()` 在循环内
  **立即** `used[c] += 1`，因此同一轮的后续位置会避开刚用过的组合；
  而 `position_entropy` 是在 10 个位置都选完之后才统一计数，
  于是**可能在一条猜测里对同一个组合重复多次**，白丢分类机会。
* 计算代价：一轮最多只能提交 10 个位置，重复一次就少一次支持集分类。

**修复**

* 把 `position_entropy` / `adaptive_hybrid` 改成在轮内维护 `used` 的本地副本，
  并新增 `avoid` 参数让取值器优先给每个位置分配**互异**的未测试组合；
* 同时新增 `split` 取值准则：优先选能把 $C_i$ 二等分的未测试组合（探测信息最多 1 bit）。

**结果**：`position_entropy[pick_mode=split]` 从 7.530 → **6.460**，成为最优策略。

## 第 11 轮 · 规则变更：秘密序列中的组合不允许重复

**用户提示词**

> 修改游戏规则，秘密序列中的组合不允许重复；

**改动清单**

| 层 | 改动 |
| --- | --- |
| `core/game.py` | 新增规则开关 `SECRET_DISTINCT = True`、`sample_secret()`、`validate_secret()`、`is_distinct_sequence()`；模块文档补充新规则带来的两条推理 |
| `core/sequence_game.py` | 默认按互异规则生成/校验秘密；新增 `distinct=` 参数以支持规则外实验；`state()` 回报实际规则 |
| `strategies/belief.py` | `PositionBelief(unique_values=...)` + `propagate_unique()`（已安置值全局删除，迭代到不动点）；`SupportTracker(unique_values=...)`（`mark_in` 直接给重数 1） |
| `strategies/*` | 5 个策略新增 `assume_distinct` 开关；`two_phase` 新增 `auto_exact` 策略与“10 个成员即提前结束”条件；`particle_entropy` 粒子改为互异采样 |
| `engine/simulator.py` | `SECRET_MODES` 显式区分规则内外；`play_one(rule_distinct=...)` 自动注入 `assume_distinct` |
| `web/api.py` + 前端 | `/api/meta` 暴露规则与秘密生成方式；秘密校验改用 `validate_secret()`；预设与下拉选项重排 |
| 测试 | 新增 `TestSecretDistinctRule`（8 例），总计 31 例通过 |
| 文档 | 02/03/04/05/06/09、两个 README、CHANGELOG 全部同步 |

**遇到的坑（第 3 个）——规则外实验会产生假结果**

* 新规则一上，`--preset out_of_rule`（常数序列秘密）直接抛错：
  `SequenceGame` 按新规则校验秘密，把重复组合拒掉了。
* 更隐蔽的问题是：即使放过校验，策略里的“重数恒为 1 / 已安置值全局删除”推理
  在“允许重复”的秘密上**是不成立的**，会误删真值、导致解不出来——
  这会让人误以为“某策略在旧规则下不行”，其实是假设被违反。
* 解决：把“是否互异”变成一条**显式的实验配置**——
  `play_one(rule_distinct=...)` 按 `secret_mode` 自动注入策略的 `assume_distinct`；
  REST 端在用户显式传秘密时按秘密自身的性质判断。规则外实验无需手改任何策略参数。

**结论反转（本轮最重要的发现）**

| 策略 | 新规则（互异） | 旧规则（允许重复） |
| --- | --- | --- |
| `two_phase` | **5.765（最优）** | 12.785（最差） |
| `position_entropy` (split) | 6.260 | **6.460（最优）** |
| `adaptive_hybrid` | 6.550 | 7.240 |
| `naive_position` | 6.775 | 9.020 |
| `particle_entropy` | 7.045 | 8.090 |

* 两阶段策略受益 **−7.02 轮**：它原来的瓶颈（常数序列探针测重数）被规则直接消掉了；
* `count_policy` 的三种取值在规则内给出**逐局完全相同**的结果（p = 1.0000）；
* `global_prune` 的边际价值从 **−2.35 轮降到 −0.30 轮**——
  因为“已安置值全局传播”接管了主要剪枝职责；
* 教训：**报告策略排名时必须连规则一起给出**，否则结论会完全反过来。

## 第 13 轮 · 新增「逐步猜测」模式（人工录入反馈）

**用户提示词**

> 新增模式：逐步猜测，针对一个未知秘密，策略先给出首轮猜测，用户手动输入每一位状态反馈，
> 策略给出下一步猜测，直到用户全部输入为“CORRECT”，落盘后，后台记录对局；

**设计与实现**

* 关键前提：这个模式里**服务端不知道秘密**，所以不能再用 `evaluate()` 算反馈。
  为此新增 `core/sequence_game.py: HumanFeedbackGame`：只收 `(猜测, 人工反馈)`，
  与 `SequenceGame` 共享 `history` 约定，策略层完全无感（不用改任何策略）；
* 新增 `core/feedback.py`：把人类输入解析成规范反馈，并用**与秘密无关的必然规律**做校验
  （四条规律见 [10 文档](10_逐步猜测模式.md)）；
* 新增页面 `/human` + 9 个 `/api/human/*` 接口；落盘写 `runtime/games/<gid>.json`
  与 `Doc/08`、`_data/events.jsonl`（`core/journal.py: archive_game / record_human_game`）。

**遇到的坑（第 5 个）——校验器的“全为 M”误判**

* 第一版校验规则写成“重复组合的位置要么全是 M、要么全是 P/W，否则报错”，
  实现时误把“全部是 M”也当成混用，导致**真实反馈被误报**。
* 定位手段：写了一个诊断脚本（`make_secrets` + `evaluate` 把真实反馈喂进 `HumanFeedbackGame`），
  在 4 个策略 × 30 局上找第一次误报，输出出错的那一轮猜测/反馈/秘密。
  一次就拿到了反例：两位都猜 `(4,4)`、反馈都是 `M`（该组合在支持集但正确位置不在这两位）。
* 修正：无 C 时只在“同时又 M 又 P/W”时才报错；并且把这条守门用例固化成测试
  （`test_full_flow_all_strategies` 要求真实反馈的每一轮 `warnings == []`）。
* 教训：**“校验器”必须先证明自己不会误报**，否则用户会直接关掉它，校验就彻底失效。

**遇到的坑（第 6 个）——两阶段策略会挪动“已确定”的位置**

* 逐步猜测模式暴露了一个旧问题：`two_phase` 阶段 A 组装批次时，
  会把它已经确认（候选集收缩为单元素）的位置也拿去试探新组合。
  对引擎无所谓，但人工模式下“上一轮已经标了 C 的位置忽然换了组合”很让人怀疑工具丢了信息。
* 修正为：默认**沿用已锁定位置的唯一候选**，并把原来那种更激进的行为做成参数
  `lock_known_positions`；实测关掉它能快 **0.360 轮**（6.125 → 5.765，p<0.0001）。
* 决定：默认保留 `True`（语义干净、人工模式友好），文档里把两种变体都报出来。

**测试**：新增 `tests/test_human_mode.py`（30 例），总数 61 例全部通过。
其中包含严格模式拒绝矛盾反馈、撤销后重录、存档可回读、真实反馈零误报等守门用例。

## 第 14 轮 · 复盘一局真实对局：逆向推测每轮的选择依据

**用户提示词**

> 分析本轮对局，逆向推测在每一轮选择当前组合的依据
> （附：`runtime/games/cf2d34c94be5.json`，标签 `260920-00`，`two_phase`，7 轮解出）

**思路：先让“解释”可被证伪，再写结论**

* 逆向推测有两种做法：人读代码去“猜”策略在想什么（不可证伪），
  或**让策略自己说出理由**（可回放、可校验）。选了后者，分三步做：

1. **先验证回放确定性**：用存档里的策略与参数重放整局，发现
   用 `seed=None/0/7/42/12345` 时第 1–5、7 轮**逐位完全一致**，只有第 6 轮不同；
   而 `seed=1` 能 7 轮全中。
   ⇒ 结论有据：**7 轮里 6 轮是约束逼出的必然选择，只有第 6 轮存在随机平局**。
   这也给后面的解释定了口径——必然轮次可以给出唯一原因，平局轮次要说明“为什么随便选都行（或都差不多）”。
2. **给策略加解释钩子**：`two_phase` 新增 `self.explain`，
   打开后每轮在 `strategy.last_decision` 留下阶段、支持集状态、逐位置候选集大小与
   一句中文理由（已锁定 / 批次分类 / 填位 / 指派 / 退化）。
   钩子**纯只读**，并专门写了测试断言“解释开与关，逐轮猜测完全一致”——
   否则“解释”本身就可能改变行为，分析结果自相矛盾。
3. **写分析器** `experiments/analyze_game.py`：回放 + 种子对照 + 解释导出 + 一致性自检，
   一键生成 `Doc/11_对局复盘_<标签>.md`。

**本局复盘结论（详见 [11 文档](11_对局复盘_260920-00.md)）**

* 第 1–4 轮全是**阶段 A（定支持集）**：每轮把 10 个互异组合放进 10 个位置，
  一次拿到 10 个“属于/不属于支持集”的判定；第 1 轮之所以是 `CANDIDATES[:10]`，
  是因为初始时 45 个未知组合的“覆盖面/使用次数”全部并列，原序决定次序。
* 第 5 轮只剩 5 个未知组合，批次填不满 10 位：**已锁定成单元素候选的位置继续沿用**
  （白拿 6 个 CORRECT），另外 4 位（⚠）用来放批次组合，同轮必然不是 C——
  这是阶段 A 的取舍：用几位的“白拿分”换一个组合的分类。
* 第 6 轮进入**阶段 B（定顺序）**：支持集已满 10 个，只剩 3 个位置（1/8/10）未锁定，
  而这 3 个位置的可能组合合起来只有 `(1,10) (4,10) (3,4)` 三个，
  于是第 8、10 位都填了 `(4,10)`（重复值本身会给出 M，用来消去，不浪费）。
  第 7 轮全部位置都是单元素候选 ⇒ 全 C 收尾。
* 决策构成统计：批次分类 44/70（62.9%）、已锁定 23/70（32.9%）、指派 2、退化 1。
  **三分之一的决策是“免费的正确”，三分之一靠主动探测**，这正是两阶段策略在互异规则下最强的原因。

**遇到的坑（第 7 个）——分析器自己的快照慢了一轮**

* 第一版分析器在调用 `next_guess()` **之前**抓信念快照，而策略的
  `_sync(history)` 是在 `next_guess()` 内部才把上一轮反馈吃进去的，
  于是快照内容整体“慢一轮”，一致性自检在真实对局上报出 **50 处假问题**
  （例如“第 1 位标为 MISPLACED 但该组合仍在候选集里”）。
* 修正：抓快照前先显式 `strategy._sync(history)`。同一局的 50 处问题全部消失（0 问题）。
* 教训：**报表数字必须和决策时刻对齐**，差一轮就会得出完全错误的结论；
  而“自检必须是能报错的”（另写用例人为制造矛盾，确认自检真的会红）。

**顺带修掉的真 bug——`count_lower` 重复计数**

* 第 6/7 轮报告里出现**负的剩余副本数**（如 `(1,10):-1`）正是解释钩子暴露出来的：
  `PositionBelief.count_lower` 每次见到 CORRECT 就 +1，
  于是一个位置在第 5、6 轮都被 CORRECT 确认时，计数变成 2，剩余副本数变成 −1。
* 修正为**按位置去重**计数（同一位置重复命中不重复计数）。
  规则内行为不变（该值只用于 `>0` 判断，实测 200 局仍为 6.125 轮），
  但报告数字恢复可信；规则外 `count_policy="exact"` 的路径也因此更准确。

**测试**：新增 `tests/test_analyze_game.py`（10 例）：解释钩子不改变行为、
每位都有且理由点对了组合、阶段 B 预算非负、`count_lower` 重复确认不超过 1、
真实回放零误报、人为矛盾必被抓到、存档回放能复现、报告含全部轮次、CLI 端到端可写盘。
总数 61 → **71 例全部通过**。

## 第 15 轮 · 候选组合矩阵（10×10）与逐轮状态着色

**用户提示词**

> 1. 沙盒的候选组合中，将55个选项排列成“10×10”的规整表格，其中“2-1”与“1-2”，“3-6”，“6-3”状态一致，
>    点选“6-3”，“5-4”等，即选择“3-6”，“4-5”；隐藏掉的10个状态（在10×10表中为20个状态，显示为灰色）
> 2. 每轮完成猜测序列后，如果为“WRONG”，则在对应位置将该选项标记为红色，如果为“MISPLACED”，
>    则标记为蓝色，如果为“CORRECT”，则标记为绿色，如果为“PARTIAL”，则标记为紫色；（颜色标记不影响交互选择）；
> 3. 沙盒中的手动试玩与策略自动均保留此更改；
> 4. 逐步猜测一栏，同样新增45个候选的状态标识（10×10布局）；

**设计与实现**

* 先确认了一条**数据前提**：组合是无序对（`core.game.ALL_COMBOS` 只存 `a<=b`），
  所以 10×10 表里 `(a,b)` 与 `(b,a)` 必然等价；又检查出被删除的 10 个组合**全是 `a<b`**，
  因此它们在表里各占 2 格 —— 正好是用户说的「20 个状态灰色」。这条前提固化成测试，
  以后若有人把对角线组合加进删除集合，灰色格数一变就会被拦下来。
* 抽了一个共用组件 `static/js/combogrid.js`（沙盒与逐步猜测共用），只做三件事：
  规范化等价对（`canonicalCombo`/`comboKey`）、累积标记（`accumulateMarks`/`overlayMarks`）、
  渲染 10×10 表（`renderComboMatrix`）。**后端未改一行**：`/api/meta` 里的
  `objects`/`allCombos`/`removedCombos` 就够排版，着色数据直接用已有的 `game.history` / 存档 `trace`。
* 着色做的两个额外决定（用户没指定，但直接影响好不好用）：
  1. **按强度累积**：同一组合可能先被判 `M`（在别的位）、后在正确位判 `C`，
     格子按 `C > M > P > W` 显示最强的一个，全部轮次写进 tooltip；否则格子颜色会被"最后一次反馈"随机覆盖。
  2. **逐步猜测页录入时就着色**：不等提交，标一位就即时叠加（tooltip 标"待提交第 k 位"），
     提交后转成"第 r 轮第 k 位"。这正是逐步猜测模式最需要的东西——边录边能看出来自己标没标反。

**统一配色（顺带修掉的不一致）**

* 原配色是 `MISPLACED=橙`、`PARTIAL=蓝`、`WRONG=灰`，与用户要求的
  `M 蓝 / P 紫 / W 红` 不符。这次把它们统一成一份变量（`--c/--m/--p/--w`），
  历史行、槽位、反馈按钮、页脚图例与矩阵**一起改**，避免出现"矩阵蓝、历史橙"的两套语义；
  警告横幅改用独立琥珀色（原先借用了 `--m` 的橙色，改蓝后会变成蓝色警告，很怪）。

**浏览器验证（逐条对应需求）**

* 矩阵 11×11（含表头）；灰色格 **20** 个且全部 `disabled`；对角线 10 格。
* 点「6-3」→ 槽位填入 `3·6`；点「5-4」→ 填入 `4·5`；两个对称格同时获得蓝色描边（状态一致）。
* 手动试玩提交一轮（反馈 `WWWWPWMWMW`）：矩阵 10 个组合着色，对称两格颜色一致
  （`1-8` 与 `8-1` 同为蓝、`1-6` 与 `6-1` 同为紫）。
* 策略自动跑完一局（two_phase，6 轮）：矩阵累积绿 19 / 红 28 / 紫 24 格。
* 逐步猜测：录入未提交时即时着色，提交后转为轮次记录，并高亮下一轮猜测；
  查看 7 轮存档时矩阵为 20 绿 / 29 紫 / 20 红。
* 计算样式核对：`--c #2ecc71`、`--m #4d9fff`、`--p #a06bff`、`--w #ff5c5c`。

**测试**：新增 `tests/test_ui_matrix.py`（12 例）——数据不变量（10 对象、删除组合全为 `a<b`、
45 候选含 10 对角线）、`/api/meta` 字段契约、模板挂载点、**脚本加载顺序**
（`combogrid.js` 必须排在页面脚本之前，否则页面会直接报 `renderComboMatrix is not defined`）、
配色常量与图例一致性。总数 71 → **83 例全部通过**。

**文档**：新建 [12 文档](12_候选矩阵与状态着色.md)（功能说明）；`05`（沙盒与前端实现）、
`10`（逐步猜测用法）同步修改；README 索引 + CHANGELOG 1.4.0。

## 第 16 轮 · 多策略并排 + 手动对局交给策略 + 逐步猜测输出理由

**用户提示词**

> 1.我想在沙盒的策略自动中，一局游戏同时运行多个策略，且面板中显示多个策略的对局历史、猜测序列、候选组合矩阵；
> 2.手动试玩模式下，可以将对局历史交给某个策略，并使用该策略进行下一步预测；
> 3.逐步猜测模式下，解释器输出每一步这么选择的理由（原因）

**总体思路**

* 三条需求看起来是三件事，其实共享同一个基础：**策略要能被“喂历史”并说清自己的依据**。
  所以先把「解释」做成所有策略共用的框架（需求 3），再让多策略面板与手动接管复用它。

**需求 3：解释框架（先做，因为是另两个的地基）**

* 原实现只给 `two_phase` 写了私有钩子（`_explain_*`），其它策略没有解释。
  这一轮把钩子提到基类，并把主循环改成**模板方法**：
  `next_guess = _sync → explain_begin → compute_guess → explain_end`，
  策略只实现 `compute_guess`，用 `note(i, 理由)` / `note_extra(键, 值)` 上报依据。
  → 好处：**解释对所有策略一律生效**，不会出现“新写的策略忘了加解释”。
* 三条铁律并全部固化成测试：**只读**（开解释不改变任何一步下法）、
  **完整**（10 位都有理由且点明本轮组合）、**可 JSON 化**（存档/前端/复盘脚本共用）。
  为守“只读”，做法是在**既有计算路径上顺手记录**，而不是事后重算
  （重算会多消耗随机数，下法就变了）。
* 每个策略说的理由不一样，这是重点：`position_entropy` 给出
  “二等分收益 0.946 bit、并列 3 个取用过更少的”，`adaptive_hybrid` 区分“探测位/定位位”，
  `particle_entropy` 给出“该位粒子数 4、后验占比 8%”，`naive_position` 说“最少使用”，
  `random`/`fixed_cycle` 老实说“本策略完全不看反馈”。

**需求 1：多策略并排（`mode=multi`）**

* 新增 `MultiGameSession`：把 N 个 `GameSession` 挂在**同一条秘密**下，
  这正是 `engine.simulator.run_benchmark` 的配对设计，只是搬到了界面上。
* 接口：`POST /api/games {mode:"multi", plan:[{key,params}]}`、`step`（全部或 `only:i`）、`play`；
  状态用 `entries[]` 返回。
* 前端：`#planList` 增删策略与参数 + `#multiGrid` 每策略一张卡片，
  卡内并排 **本轮猜测（反馈颜色）/ 10×10 矩阵 / 历史 / 该轮理由折叠面板**。
  矩阵为了能一屏放几张，加了 `.cg-compact` 紧凑样式。

**需求 2：手动试玩交给策略（`POST /api/advise`）**

* 服务端不需要知道秘密：拿历史重放策略信念即可，所以这个接口也能用来分析
  “人工逐步猜测”里保存的对局。
* **关键坑**：一开始直接 `strategy.next_guess(history)`，结果与“自己玩到那一步”不同——
  策略内部有状态（`used` 计数、随机数流），一次性喂历史会跳过前面几轮的随机数消耗。
  改成**按历史逐步重放**（`for step: next_guess(history[:step])` 再 `next_guess(history)`），
  测试断言“重放 == 直接对局”逐位一致（连解释里的候选集大小都比对）。
* 前端填入 10 个槽位后**仍可手动修改**，并同步展示逐位理由。

**测试**：新增 `tests/test_explain_and_multi.py`（15 例）。总数 83 → **98 例全部通过**。

**验证“解释没有改变行为”**：插桩后重跑 200 局基准，5 个策略的平均轮次与插桩前**逐位一致**
（6.125 / 6.260 / 6.550 / 6.775 / 7.045）；`explain=True` 的额外耗时约 +2%（粒子）～ +59%
（两阶段，绝对值 1 ms/局 → 1.5 ms/局）。

**文档**：新建 [13 多策略并排与策略接管](13_多策略并排与策略接管.md)、
[14 决策解释与逐步理由](14_决策解释与逐步理由.md)；`03/05/10` 同步更新；CHANGELOG 1.5.0。

## 第 17 轮 · 子页签化、卡片独立、CORRECT 锁定、移除两个无用策略

**用户提示词**

> 1.“所有策略各走一步”的按钮位于导航栏，控制时不够方便（不能在同一画面页显示），
>    且3种模式公用一个顶部栏，我想将3种模式分为3个子导航页签，便于交互与控制。
> 2.沙盒页有3个相互独立的子页签，每个子页签内卡片相互独立；
> 3.所有模式下，当猜测正确，则锁定当前这个位置的选项，不可选择其他组合；
> 4.移除随机基线和固定循环2种不使用反馈的策略，基本是随机策略，也不能在一个位置不断重复错误的选择；

**需求 1+2：三个子页签 + 卡片独立**

* 原来三种模式共用一个顶部工具条，「所有策略各走一步」在最上面、它控制的卡片在最下面。
  现在改成三个子页签，**每个页签自带工具条 / 状态栏 / 卡片区**：
  * ① 手动试玩：种子、轮次上限、显示秘密、把历史交给策略、开新局、提交猜测、清空未锁定槽位；
  * ② 策略自动：策略+参数、种子、上限、开新局、走一步、自动跑完；
  * ③ 多策略对比：种子、上限、开新局、**所有策略各走一步**、自动跑完 + 策略清单面板。
* “卡片相互独立”落到了 DOM 与状态两层：`sandbox.js` 拆成 `SingleView`（手动/自动各一个实例）
  与 `MultiView`，每份卡片用 `data-role` 定位，互不影响；切页签只切显示，**各页签各自保留对局与槽位**。

**需求 3：CORRECT 锁定**

* 规则：某位一旦判定 CORRECT，**这个位置就定了**——不许再改成别的组合。
* 三处表现：手动模式槽位点不动（弹提示）+ 矩阵点选**跳过**锁定位置 + 「清空」只清未锁定项；
  策略自动与多策略卡片的锁定位置显示 🔒；逐步猜测页对锁定位置显示 🔒 并**自动预填 C**
  （人工录入的是事实，仍允许修正，否则误录就救不回来了）。
* 关键设计：锁定**完全由历史推导**（`feedback == CORRECT` 的位置），
  所以撤销一轮后锁定自动解除，界面永远等于历史事实，不需要额外状态。

**需求 4：移除两个不使用反馈的策略**

* 删掉 `random` / `fixed_cycle`：完全不看反馈 ⇒ 在 $45^{10}$ 里不可能解出，
  只占满轮次上限；而且它们会在同一位置反复填同一个错误组合，与真实可用策略差距过大。
* 连带改动：注册表 `CLASSES`、`DEFAULT_PLAN_KEYS`、命令行 `greedy_vs_adaptive` 预设、
  `/api/experiments/presets`、策略库页（现 5 张卡片）、`Doc/01/03/06/09/14` 与 `README`。
  **历史日志不改写**——`Doc/08` 与 `Doc/06` 里那些 0% 解出的旧结果是当时真实跑出来的。

**遇到的坑（第 8 个）——一次“模糊匹配”的批量替换把一行代码改坏了**

* 现象：页面白屏，浏览器只报 `SyntaxError: Unexpected token '.'`，控制台不给行号；
  `toast` 里也只有一句 `Cannot read properties of null (reading 'addEventListener')`，
  而所有 `id` 都确实存在。
* 定位手段：①把异常栈塞进 toast → 拿到是 `SingleView.bind`；
  ②把 JS 源码**当内联 `<script>` 注入**并监听 `error` 事件 → 拿到准确的**行号/列号**，
  一眼看到那一行变成了 `state.views.manual(e && e.stack) || .updateButtons();`。
* 根因有两处：其一是我在批量替换里把「调试用的栈”**回退**时匹配错了位置，
  把 `state.views.manual.updateButtons()` 改坏了；其二是 `SingleView.bind()` 假设两个页签
  都有 `#…-btnClear`/`#…-btnPlay`，但策略页签本来就没有“清空槽位”按钮。
  两者都改成“先查存在性再绑定/再禁用”。
* 教训：**模板方法化的 UI 里，可选控件必须做存在性判断**；
  以及批量替换后要用 `new Function(src)` 或内联脚本注入做一次**语法自检**，比看现象快得多。
