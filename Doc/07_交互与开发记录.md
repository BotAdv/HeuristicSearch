## 第 1 轮 · 需求提交（用户提示词原文）

> python环境 conda activate  flask_env
>
> 我们正在研究一个“组合猜序列”游戏，需要你用 Flask + 前端搭建一个可扩展的沙盒环境，用于验证不同启发式搜索策略的性能。
>
> **【游戏规则】**
> 1. 对象集合 U = {1,2,...,10}。
> 2. 一个“组合”是从 U 中允许重复地选两个对象，不计顺序，表示为 (a,b)，1 <= a <= b <= 10。
> 3. 全部组合共 C(11,2) = 55 个，包含 10 个自组合 (1,1),(2,2),...,(10,10)。
> 4. 本游戏预先删除以下 10 个组合，玩家已知它们不可用：(1,5), (2,4), (3,7), (4,6), (5,6), (6,8), (7,10), (8,9), (8,10), (9,10)。因此实际候选组合集合 S 共 45 个。
> 5. 秘密序列 x = (x_1,...,x_10) 是长度 10 的序列，每个 x_i 从 S 中选取，允许重复。
> 6. 玩家每轮提交一个猜测序列 g = (g_1,...,g_10)，每个 g_i 从 S 中选取。
> 7. 对每个位置 i，反馈按以下优先级判定，高优先级覆盖低优先级：
>    (1) 完全正确：g_i == x_i
>    (2) 正确但位置错误：g_i != x_i，但存在 j != i 使得 g_i == x_j
>    (3) 部分正确：g_i != x_i，且 g_i 不在其他任何位置出现，但 g_i 与 x_i 至少共享一个元素
>    (4) 完全错误：以上都不满足
> 8. 当所有 10 个位置都返回“完全正确”时，游戏结束。
>
> **【重要】**
> - “正确但位置错误”会掩盖当前位置的真实信息，玩家无法从该位置本次反馈中得知 g_i 与 x_i 的关系。
> - 反馈是一个长度为 10 的向量，每个元素取值为 {CORRECT, MISPLACED, PARTIAL, WRONG}。
>
> **【需要验证的核心问题】**
> 1. 不同启发式策略在期望步数上的表现差异。
> 2. 是否存在比“先确定组合集合，再确定顺序”更优的混合策略。
> 3. “正确但位置错误”反馈对最坏和期望步数的影响。
> 4. 动态自适应策略与固定策略、贪心策略的对比。
>
> **【评估指标】** 平均步数（期望）、中位数步数、90 分位数、99 分位数、最坏步数、每轮信息增益（可选）、计算耗时
>
> **【策略接口】** 每个策略实现为一个类，提供方法：
> ```python
> def next_guess(self, history) -> List[Tuple[int,int]]
> ```
> 其中 history 是之前所有轮次的 (guess, feedback) 列表。策略内部可以维护自己的信念状态。
>
> //pass：记录项目过程中的所有交互信息，包括提示词、每轮反馈，将其存入根目录下的Doc文件，按照功能和任务类型进行记录，新功能则新建一个文件，对功能的修改则记录在对应功能对应说明文件中；

**处理反馈（第 1 轮）**

* 确认环境：`flask_env` = Python 3.10.20 / Flask 3.1.3 / numpy 2.2.6（无 pandas、无 scipy，
  统计部分改用标准库 `math` 手写）。
* 工作区为空目录，从零搭建；确定分层：`core`（纯规则）→ `strategies`（可插拔）→
  `engine`（实验）→ `web/templates/static`（展示）。

## 第 2 轮 · 核心规则层与单元测试

**新增文件**：`core/game.py`、`core/sequence_game.py`、`config.py`、`tests/test_game.py`

**处理反馈**

* `core/game.py` 用模块级 `assert` 锁定 55 / 45 这两个基数，把规则常量集中在一处；
* `evaluate()` 严格按优先级实现，`counts[g] > 0` 这一判断同时覆盖了
  “g_i 出现在其它位置”，避免用 `j != i` 循环造成性能损失；
* 写了 14 个规则用例，覆盖优先级、PARTIAL 的“独苗”前提、长度校验、可复现性。

**遇到的坑（第 1 个）**

* 用例 `test_partial_requires_unique_value` 首次运行失败。
  原因是**我的用例写错了**：设 $x=(1,2)^{10}$、$g=(1,3)^{10}$ 时，
  $(1,3)$ 并不在支持集中，所以正确判定是 `PARTIAL`（共享元素 1），不是 `MISPLACED`。
* 修正为：$x=((1,2),(3,3),(1,2),(4,4)^7)$、$g=((3,3),(1,2),(3,3),(4,4)^7)$，
  此时三个位置都因“组合在别处出现”判 `M`，且全序列不含 `P`。
* **教训**：`M` 与 `P` 的分界是“**该组合是否属于支持集**”，不是“是否与 $x_i$ 共享元素”。
  这条后来成了所有策略里最有价值的剪枝依据。

**结果**：23 个测试全部通过。

## 第 3 轮 · 策略层（7 个策略）

**新增文件**：`strategies/base.py`、`belief.py`、`random_strategy.py`、`fixed_cycle.py`、
`naive_position.py`、`two_phase.py`、`position_entropy.py`、`adaptive_hybrid.py`、
`particle_entropy.py`、`__init__.py`

**处理反馈**

* `Strategy` 基类提供 `_sync(history)`，只把**尚未吸收**的轮次交给 `observe()`，
  既能增量维护状态，也能在外部重置 history 时自动重建，避免策略状态与 history 不一致。
* 把易错的推理抽到共享的 `belief.py`：
  `PositionBelief`（逐位置候选集合 + 四条推理 + global_prune）与 `SupportTracker`（支持集/重数）。
* `particle_entropy` 是本项目唯一需要重计算的部分，用 NumPy 把反馈判定写成
  `evaluate_particles()`（一次算完所有粒子），单候选评分 $O(P\cdot10)$；
  粒子重采样从“逐位置候选集合的乘积分布”提议，保证真解一定在提议分布支持内。
* `SupportTracker.observe()` 里加入常数序列自动识别，使 `two_phase` 的重数探针
  只需发一个 `(c,…,c)` 就能读出精确重数。

## 第 6 轮 · 第一次基准实验：结果与预期不符

**发现**：预期“粒子滤波 + 全局最大熵”最强，实测它并不占优：

| 策略 | 平均步数 |
| --- | --- |
| 自适应混合 | 7.973 |
| 粒子滤波 + 全局最大熵 | 8.047 |
| 逐位置信息熵贪心（entropy 准则） | 8.107 |
| 朴素位置独立贪心 | 9.023 |
| 两阶段（exact） | 12.830 |

**处理反馈**

1. 先怀疑是评分目标选得不好，给 `particle_entropy` 加了 `objective` 参数
   （entropy / entropy_correct / expected_remaining / expected_correct）做消融；
2. 结果四种目标两两比较 p 值全部 > 0.19，**没有显著差异** —— 排除“目标函数”这一解释；
3. 转向消融参数，运行 `naive_position[global_prune=True]`，得到 **6.930** 轮，
   比当时所有策略都快 → 说明真正的关键不在“更复杂的建模”，而在更基本的剪枝与取值准则。

## 第 7 轮 · 定位差异：轮内重复组合

**异常**：`naive_position[global_prune=True]` 6.930，而
`position_entropy[pick_mode=least_used, global_prune=True]` 7.500 —— 两者“看起来是同一个算法”。

**定位过程**

* 逐行比对两处取值代码，发现唯一实质差异：`naive_position._pick()` 在循环内
  **立即** `used[c] += 1`，因此同一轮的后续位置会避开刚用过的组合；
  而 `position_entropy` 是在 10 个位置都选完之后才统一计数，
  于是**可能在一条猜测里对同一个组合重复多次**，白丢分类机会。
* 计算代价：一轮最多只能提交 10 个位置，重复一次就少一次支持集分类。

**修复**

* 把 `position_entropy` / `adaptive_hybrid` 改成在轮内维护 `used` 的本地副本，
  并新增 `avoid` 参数让取值器优先给每个位置分配**互异**的未测试组合；
* 同时新增 `split` 取值准则：优先选能把 $C_i$ 二等分的未测试组合（探测信息最多 1 bit）。

**结果**：`position_entropy[pick_mode=split]` 从 7.530 → **6.460**，成为最优策略。

## 第 11 轮 · 规则变更：秘密序列中的组合不允许重复

**用户提示词**

> 修改游戏规则，秘密序列中的组合不允许重复；

**改动清单**

| 层 | 改动 |
| --- | --- |
| `core/game.py` | 新增规则开关 `SECRET_DISTINCT = True`、`sample_secret()`、`validate_secret()`、`is_distinct_sequence()`；模块文档补充新规则带来的两条推理 |
| `core/sequence_game.py` | 默认按互异规则生成/校验秘密；新增 `distinct=` 参数以支持规则外实验；`state()` 回报实际规则 |
| `strategies/belief.py` | `PositionBelief(unique_values=...)` + `propagate_unique()`（已安置值全局删除，迭代到不动点）；`SupportTracker(unique_values=...)`（`mark_in` 直接给重数 1） |
| `strategies/*` | 5 个策略新增 `assume_distinct` 开关；`two_phase` 新增 `auto_exact` 策略与“10 个成员即提前结束”条件；`particle_entropy` 粒子改为互异采样 |
| `engine/simulator.py` | `SECRET_MODES` 显式区分规则内外；`play_one(rule_distinct=...)` 自动注入 `assume_distinct` |
| `web/api.py` + 前端 | `/api/meta` 暴露规则与秘密生成方式；秘密校验改用 `validate_secret()`；预设与下拉选项重排 |
| 测试 | 新增 `TestSecretDistinctRule`（8 例），总计 31 例通过 |
| 文档 | 02/03/04/05/06/09、两个 README、CHANGELOG 全部同步 |

**遇到的坑（第 3 个）——规则外实验会产生假结果**

* 新规则一上，`--preset out_of_rule`（常数序列秘密）直接抛错：
  `SequenceGame` 按新规则校验秘密，把重复组合拒掉了。
* 更隐蔽的问题是：即使放过校验，策略里的“重数恒为 1 / 已安置值全局删除”推理
  在“允许重复”的秘密上**是不成立的**，会误删真值、导致解不出来——
  这会让人误以为“某策略在旧规则下不行”，其实是假设被违反。
* 解决：把“是否互异”变成一条**显式的实验配置**——
  `play_one(rule_distinct=...)` 按 `secret_mode` 自动注入策略的 `assume_distinct`；
  REST 端在用户显式传秘密时按秘密自身的性质判断。规则外实验无需手改任何策略参数。

**结论反转（本轮最重要的发现）**

| 策略 | 新规则（互异） | 旧规则（允许重复） |
| --- | --- | --- |
| `two_phase` | **5.765（最优）** | 12.785（最差） |
| `position_entropy` (split) | 6.260 | **6.460（最优）** |
| `adaptive_hybrid` | 6.550 | 7.240 |
| `naive_position` | 6.775 | 9.020 |
| `particle_entropy` | 7.045 | 8.090 |

* 两阶段策略受益 **−7.02 轮**：它原来的瓶颈（常数序列探针测重数）被规则直接消掉了；
* `count_policy` 的三种取值在规则内给出**逐局完全相同**的结果（p = 1.0000）；
* `global_prune` 的边际价值从 **−2.35 轮降到 −0.30 轮**——
  因为“已安置值全局传播”接管了主要剪枝职责；
* 教训：**报告策略排名时必须连规则一起给出**，否则结论会完全反过来。

## 第 13 轮 · 新增「逐步猜测」模式（人工录入反馈）

**用户提示词**

> 新增模式：逐步猜测，针对一个未知秘密，策略先给出首轮猜测，用户手动输入每一位状态反馈，
> 策略给出下一步猜测，直到用户全部输入为“CORRECT”，落盘后，后台记录对局；

**设计与实现**

* 关键前提：这个模式里**服务端不知道秘密**，所以不能再用 `evaluate()` 算反馈。
  为此新增 `core/sequence_game.py: HumanFeedbackGame`：只收 `(猜测, 人工反馈)`，
  与 `SequenceGame` 共享 `history` 约定，策略层完全无感（不用改任何策略）；
* 新增 `core/feedback.py`：把人类输入解析成规范反馈，并用**与秘密无关的必然规律**做校验
  （四条规律见 [10 文档](10_逐步猜测模式.md)）；
* 新增页面 `/human` + 9 个 `/api/human/*` 接口；落盘写 `runtime/games/<gid>.json`
  与 `Doc/08`、`_data/events.jsonl`（`core/journal.py: archive_game / record_human_game`）。

**遇到的坑（第 5 个）——校验器的“全为 M”误判**

* 第一版校验规则写成“重复组合的位置要么全是 M、要么全是 P/W，否则报错”，
  实现时误把“全部是 M”也当成混用，导致**真实反馈被误报**。
* 定位手段：写了一个诊断脚本（`make_secrets` + `evaluate` 把真实反馈喂进 `HumanFeedbackGame`），
  在 4 个策略 × 30 局上找第一次误报，输出出错的那一轮猜测/反馈/秘密。
  一次就拿到了反例：两位都猜 `(4,4)`、反馈都是 `M`（该组合在支持集但正确位置不在这两位）。
* 修正：无 C 时只在“同时又 M 又 P/W”时才报错；并且把这条守门用例固化成测试
  （`test_full_flow_all_strategies` 要求真实反馈的每一轮 `warnings == []`）。
* 教训：**“校验器”必须先证明自己不会误报**，否则用户会直接关掉它，校验就彻底失效。

**遇到的坑（第 6 个）——两阶段策略会挪动“已确定”的位置**

* 逐步猜测模式暴露了一个旧问题：`two_phase` 阶段 A 组装批次时，
  会把它已经确认（候选集收缩为单元素）的位置也拿去试探新组合。
  对引擎无所谓，但人工模式下“上一轮已经标了 C 的位置忽然换了组合”很让人怀疑工具丢了信息。
* 修正为：默认**沿用已锁定位置的唯一候选**，并把原来那种更激进的行为做成参数
  `lock_known_positions`；实测关掉它能快 **0.360 轮**（6.125 → 5.765，p<0.0001）。
* 决定：默认保留 `True`（语义干净、人工模式友好），文档里把两种变体都报出来。

**测试**：新增 `tests/test_human_mode.py`（30 例），总数 61 例全部通过。
其中包含严格模式拒绝矛盾反馈、撤销后重录、存档可回读、真实反馈零误报等守门用例。

## 待办 / 可继续探索的方向

* **每轮信息增益指标**（题目列为“可选”）目前只体现在策略内部评分，
  尚未作为报告级指标输出；可在 `metrics.py` 里累计每轮反馈的香农熵。
* `secret_mode` 可扩展为“按支持集大小分层采样”，进一步分离“重数”与“支持集”两个难度的贡献。
* `particle_entropy` 的候选猜测池可换成“逐位置候选集合上的遗传/束搜索”，
  验证瓶颈确实在搜索目标而不是信念精度。
* 加一个“对抗性秘密搜索”（对给定策略爬山搜索最难秘密）来自动生成最坏用例，
  而不是只在模拟中取最大值。
