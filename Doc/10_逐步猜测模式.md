# 10 逐步猜测模式（人工录入反馈）

> 页面：`/human` ｜ 接口前缀：`/api/human/*` ｜ 实现：`core/feedback.py`、`core/sequence_game.py: HumanFeedbackGame`、`web/api.py`、`static/js/human.js`
> 测试：`tests/test_human_mode.py`（30 例）

## 1. 为什么需要这个模式

沙盒（`/`）与批量模拟都要求**服务端知道秘密序列**，才能自动算出反馈。
但真实场景里常常是“**别人出了一个题，秘密只有他知道**”：这时候反馈只能由人来读、人来录。

逐步猜测模式就是为这种情况准备的：

```
策略给出第 1 轮猜测 ──► 你对着真实秘密逐位录入反馈 ──► 策略据此给出第 2 轮猜测 ──► …
                                                                    │
                                                          全部 CORRECT ──► 落盘 ──► 记录到 Doc/
```

**服务端全程不知道秘密**，它只拿到 `(猜测, 反馈)` 序列。这一点与规则层的设计一致：
策略本来就只能通过 `history` 观察游戏。

## 2. 页面用法

1. 选策略（可用参数与策略库/实验台完全一致）、填一个对局标签、按需勾选三个开关：
   * **严格校验**：反馈与已有记录矛盾时**直接拒绝**该轮（保证数据质量）；
   * **自动落盘**：全部位置标为 CORRECT 时自动保存并记录（默认开）；
   * **秘密组合互异**：声明这个秘密满足当前规则。如果对方给的秘密本身有重复组合，
     取消勾选（等价于把策略的 `assume_distinct` 置为 False）。
2. 点「开始新对局」——策略立刻给出第 1 轮猜测。
3. 为 10 个位置逐一选反馈：每个位置都有 `C M P W` 四个按钮；
   也可以用「快速录入」框直接输入/粘贴 10 个字母（如 `CMPWCMPWCM`）；
   最后一轮常按「全部标为 CORRECT」。
4. 点「提交反馈」（或按 `Enter`）。策略会自动给出下一轮猜测。
5. 全部 CORRECT 后自动落盘；未解出时也可以随时点「落盘并记录」。
6. **「决策解释」面板**：逐位列出当前待反馈猜测“为什么这么选”；
   历史里每一行尾部也有「理由」按钮，可以回看任意一轮的依据（详见 [14 文档](14_决策解释与逐步理由.md)）。

其它操作：

* **撤销上一轮**（或按 `Backspace`）：把最后一轮退回，并**恢复成“等待该轮猜测的反馈”**
  状态，方便你直接重录；若已经没有轮次可撤，则退化为“丢弃当前待反馈的猜测”；
* **已落盘对局**：右上角表格列出所有存档，点「查看」可以回看整局轨迹。

### 2.1 候选组合矩阵（10×10）

页面中部的「候选组合矩阵」把 45 个候选与 10 个被删除组合排成 10×10 表
（行 = 前一位 `a`，列 = 后一位 `b`；`a-b` 与 `b-a` 是同一个组合，两格状态一致）：

* **每轮提交后**，按逐位反馈给对应组合着色：`C` 绿 · `M` 蓝 · `P` 紫 · `W` 红；
* **录入过程中**（还没提交）就已经实时叠加，tooltip 会标“待提交第 k 位”，
  方便边录边核对；提交后转为“第 r 轮第 k 位”；
* 同一组合被多轮标记时显示最强的那个（`C > M > P > W`），其余记录在 tooltip 里；
* 矩阵只是**看板**（本页不可点选），颜色不影响任何交互；
* 查看已落盘对局时，矩阵同步切换为该存档的标记。

详细约定（等价格语义、色值、累积优先级）见 [12 文档](12_候选矩阵与状态着色.md)。

## 3. 反馈一致性校验（关键设计）

秘密未知，服务端没法用 `evaluate()` 验真，但可以检查**与秘密无关的必然规律**。
`core/feedback.py: FeedbackChecker` 维护“哪些组合属于支持集”“哪些位置已定位”，
对每一轮做四项检查：

| # | 规律 | 依据 | 违反示例 |
| --- | --- | --- | --- |
| 1 | 同一个组合在一轮里出现多次时：①至多一个 CORRECT；②若有一个 CORRECT，其余必须是 MISPLACED；③若没有 CORRECT，则要么**全是 MISPLACED**（该组合在支持集但在别处），要么**全是 PARTIAL/WRONG**（该组合不在支持集，此时 P/W 可任意混） | 反馈优先级 + 重数恒为 1 | 两位都猜 `(4,4)` 却都标 C；或一位标 M、另一位标 P |
| 2 | 某组合一旦出现过 `C`/`M`，它就**属于**支持集，之后猜它不可能出现 `P`/`W`；反之亦然 | `M`/`P` 的定义 | 第 1 轮 `(1,8)` 标了 W，第 3 轮又标 C |
| 3 | 出现过 `C` 就钉死“位置 ↔ 组合”：同一个组合不能再出现在别的位置的 `C`，同一个位置再出现 `C` 时必须是同一个组合 | 重数恒为 1 | 第 1 位已确认 `(1,1)`，第 5 轮又把 `(1,1)` 标 C 在别处 |
| 4 | 整轮全标 `CORRECT` 时，该猜测必须是一个合法秘密（互异规则下即 10 个组合互不相同） | 当前规则 | 猜测里有重复组合却整轮全 C |

**默认只警告不拒绝**（`strict=false`）：警告会显示在页面上、写进落盘记录的 `warnings` 字段，
方便事后统计录入质量。勾选「严格校验」后，矛盾的那一轮会被**退回**（不进入历史），
并且**保留同一个猜测继续等待反馈**，你只要改正后重新提交即可。

> 校验器只做“必然规律”检查，因此**不会误报真实反馈**。
> `tests/test_human_mode.py` 用“隐藏秘密 + 真实反馈”跑了 4 个策略共 120 局，
> 要求每一轮 `warnings == []`，专门守这条底线。

## 4. 落盘与记录

点「落盘并记录」（或全 CORRECT 时自动触发）会做三件事：

| 产物 | 内容 |
| --- | --- |
| `runtime/games/<gameId>.json` | 完整对局存档（策略、参数、逐轮猜测与反馈、每轮警告、支持集推断、时间戳） |
| `Doc/08_对局与模拟日志.md` | 追加一节《逐步猜测对局》：结果、支持集推断、逐轮猜测/反馈/校验结论表格 |
| `Doc/_data/events.jsonl` | 追加一条 `kind = "human_game"` 的记录，便于二次分析 |

存档结构（节选）：

```json
{
  "gameId": "a1b2c3d4e5f6",
  "mode": "human-feedback",
  "label": "朋友出的题 01",
  "strategy": "two_phase",
  "params": {"count_policy": "auto_exact"},
  "assumeDistinct": true,
  "secretKnown": false,
  "solved": true,
  "rounds": 6,
  "support": {"knownIn": 10, "knownOut": 21, "placed": 10},
  "trace": [
    {"index": 1, "guess": [[1,1], ...], "feedback": ["WRONG", ...],
     "letters": "WWMWPWWPW", "warnings": []}
  ]
}
```

## 4.1 复盘这一局：策略为什么这么下

存档里的 `strategy` + `params` 足够把整局**原样回放**一遍，于是可以逐轮问策略“你为什么选这个”：

```powershell
python experiments/analyze_game.py a1b2c3d4e5f6          # 也可传存档路径
# -> Doc/11_对局复盘_<标签>.md
```

报告包含四块：回放是否复现（多种子对照，区分“必然选择”与“随机平局”）、
每轮每个位置的候选集规模与选择理由、各轮反馈让候选集收缩了多少、决策构成统计。
`two_phase` 已实现解释钩子，其它策略暂只会给出信念快照（可自行实现，见
[03 文档 1.1 节](03_策略库说明.md)）。

## 5. 接口一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/human/games` | 新建对局（默认立刻让策略给出首轮猜测） |
| GET | `/api/human/games/<gid>` | 查询状态：`status` / `pendingGuess` / `history` / `roundWarnings` / `support` |
| POST | `/api/human/games/<gid>/next` | 让策略给出本轮猜测 |
| POST | `/api/human/games/<gid>/feedback` | 录入本轮反馈（`{"feedback": "CMPW…"}` 或 10 元素数组） |
| POST | `/api/human/games/<gid>/undo` | 撤销上一轮（并恢复该轮猜测为待反馈） |
| POST | `/api/human/games/<gid>/save` | 落盘并记录（未解出也可保存） |
| DELETE | `/api/human/games/<gid>` | 删除会话（不动已落盘的存档） |
| GET | `/api/human/archive` | 已落盘对局列表 |
| GET | `/api/human/archive/<gid>` | 某局的完整存档 |

`status` 有三种取值：`awaiting_guess`（该策略出招）、`awaiting_feedback`（该你录入）、`solved`。

示例（命令行驱动一整局）：

```bash
curl -X POST http://127.0.0.1:5000/api/human/games \
  -H "Content-Type: application/json" \
  -d '{"strategy":"two_phase","label":"命令行对局","strict":false}'
# -> {"gameId":"...","status":"awaiting_feedback","pendingGuess":[[..],..], ...}

curl -X POST http://127.0.0.1:5000/api/human/games/<gid>/feedback \
  -H "Content-Type: application/json" -d '{"feedback":"WWMWPWWPWM"}'
# -> {"accepted":true,"warnings":[],"round":{...},"state":{...}}

curl -X POST http://127.0.0.1:5000/api/human/games/<gid>/next -d '{}' -H "Content-Type: application/json"
```

## 6. 与其它两种模式的区别

| | 沙盒 `/` | **逐步猜测 `/human`** | 实验台 `/lab` |
| --- | --- | --- | --- |
| 秘密来源 | 服务端随机/指定 | **未知，只在你手上** | 服务端按种子批量生成 |
| 反馈来源 | 规则自动判定 | **人工录入** | 规则自动判定 |
| 节奏 | 一步/整局 | **一步一轮，策略与人对答** | 整批跑完 |
| 校验 | 无需校验 | **一致性规律校验（4 条）** | 无需校验 |
| 产出 | 逐轮日志 | **对局存档 + 逐轮日志 + 事件流** | 指标表 + 图表 + CSV/JSON |
| 用途 | 手动试玩、观察策略 | **评估“别人出题”时的真实表现** | 期望/分位/最差步数对比 |

## 7. 实测：逐步猜测下的策略表现

逐步猜测模式里“人”只是反馈的搬运工，反馈与自动模式**完全等价**
（只要录入正确），因此各策略的步数分布与实验台一致：
`two_phase` 最快（默认 6.13 轮，关闭 `lock_known_positions` 后 5.77 轮），
`particle_entropy` 最慢（7.05 轮）。见 [06 实验结论](06_实验结论与复现指南.md)。

这个模式真正的价值在于：**当秘密不在系统里时，仍然可以收集可用于研究的完整对局数据**，
而且每轮都带一致性校验结论，可以量化人工录入的错误率。
