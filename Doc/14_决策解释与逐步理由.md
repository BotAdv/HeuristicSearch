# 14 · 决策解释：每一步为什么这么选

> 需求：*「逐步猜测模式下，解释器输出每一步这么选择的理由（原因）」*。
> 这一版把“解释”做成了**所有策略共用的一套框架**，逐步猜测页与沙盒都能逐轮查看。
> 相关代码：`strategies/explain.py`、`strategies/base.py`（模板方法 + 钩子）、
> 各策略里的 `note()/note_extra()`、`static/js/api.js: renderDecision()`。

## 1. 三条硬性约束

解释系统最容易犯的错是“解释本身改变了行为”，或者“解释是事后编的”。这里定了三条规矩，
并且都用测试守住（`tests/test_explain_and_multi.py`）：

1. **只读**：`explain` 打开后不调用任何随机数、不改信念/计数。
   做法是**在既有计算路径上顺手记录**，而不是“重算一遍”（重算会多消耗 RNG，导致下法不同）。
   → 测试：7 个策略 × 3 条秘密，`explain` 开/关逐轮猜测必须完全一致。
2. **完整**：每一轮的 10 个位置都必须有理由，且理由要点明**本轮实际填的那个组合**。
   → 测试：逐策略校验 `reason` 非空且包含 `(a, b)`。
3. **可机器消费**：`last_decision` 必须能直接 JSON 序列化（存档、前端、复盘脚本共用）。
   → 测试：`json.dumps(last_decision)`。

## 2. 统一入口：模板方法 + 钩子

策略不再自己实现 `next_guess`，而是实现 `compute_guess`；基类用模板方法包一层：

```python
# strategies/base.py
def next_guess(self, history):
    self._sync(history)            # 吸收新反馈（策略自己的信念更新）
    self.explain_begin(history)    # explain=False 时直接返回，零开销
    guess = self.compute_guess(history)
    self.explain_end(guess, history)   # 补全空缺理由 + 组装 last_decision
    return guess
```

好处：**解释对所有策略一律生效**，不会出现“某个策略忘了写解释”；
并且 `explain=False` 时只有两次极廉价的函数调用（实测开销 < 1%）。

策略侧只需要按需调用两个方法：

```python
self.note(i, "……中文理由……")      # 给第 i 个位置（0-based）记一条理由
self.note_extra("batch", {...})    # 记一条与位置无关的额外统计
```

## 3. 输出结构

```pythonc
{
  "round": 3,                        // 这是第几轮
  "strategy": "two_phase",
  "strategyName": "两阶段：先定支持集再定顺序",
  "phase": "A" | "B" | null,         // 阶段性策略才有
  "support": {"inList": [...], "inCount": 5, "outCount": 15, "unknownCount": 25, "counts": {...}},
  "candidates": [                    // 与 10 个位置一一对应（决策时刻的信念）
    {"position": 1, "size": 28, "chosen": [2, 10], "inCandidateSet": true,
     "reason": "批次分类：(2, 10) 还没判定过是否属于支持集，且它仍在本位置候选集内",
     "topCandidates": [[1,1],[1,2], …]}
  ],
  "batch": {...}, "budget": {...}, … // 各策略自报的额外统计
}
```

`inCandidateSet=false` 表示该组合**不在**这个位置的候选集里——这是“纯探测”，
本轮这一位必然不是 CORRECT，界面会打 ⚠ 提醒（不是策略失误，是主动换取分类信息）。

## 4. 各策略具体说了什么

| 策略 | 理由类型 | 例子 |
| --- | --- | --- |
| `two_phase` | 已锁定 / 批次分类 / 填位 / 指派 / 退化 | `批次分类：(2, 10) 还没判定过是否属于支持集，且它仍在本位置候选集内` |
| `position_entropy` | split 二等分 / 最大熵 / 最少使用 | `split 二等分：(1, 3) 能把本位置 45 个候选按“与它共享对象/不共享”切成 16/28，二等分收益 0.946 bit（最高，并列 3 个取用过更少的）` |
| `adaptive_hybrid` | 探测位 / 定位位 + 上面三种准则 | `探测位：本位置候选 16 个 > 阈值 1，改填尚未分类的 (6, 6) 去换一次支持集判定（它仍可能出现在 6 个位置）` |
| `naive_position` | 最少使用 / 随机 / 首项 | `最少使用：本位置候选 45 个里 (3, 6) 全局只用过 0 次（最少，并列 45 个等概率取一个）；尚未判定它是否属于支持集` |
| `particle_entropy` | 粒子后验边缘分布 / 收敛判定 | `粒子后验：本位置出现最多的是 (2, 7)（64 个粒子里 5 个，8%）；次优：(2, 10) 4、(3, 6) 4；本轮取 (3, 6)（该位粒子数 4）` |
| `random` / `fixed_cycle`（已移除，见 [03 文档 3.1](03_策略库说明.md)） | 兜底：说明“本策略不使用反馈” | `随机基线（本策略完全不看反馈，每个位置独立均匀随机）：本轮填 (3, 6)` |

额外统计（`note_extra`）会以标签形式展示，例如
`本批：未判定 45 个 → 选中 10 个`、`尚未安置副本的组合 2 个`、
`particles=64，candidatePool=32，objective=entropy_correct，bestScore=5.867`。

## 5. 在哪里能看到

| 位置 | 展示方式 |
| --- | --- |
| 逐步猜测页 | 「决策解释」面板默认显示**当前待反馈猜测**的逐位理由；历史每行有「理由（第 n 轮）」按钮可回看任意一轮 |
| 沙盒 · 策略自动 | 每走一步自动展开该步的理由；历史每行也有「理由」按钮 |
| 沙盒 · 手动试玩 | 点「让策略预测下一步」后展示该预测的逐位理由（见 [13 文档](13_多策略并排与策略接管.md)） |
| 沙盒 · 多策略对比 | 每张卡片底部「第 n 轮：为什么这么选」折叠面板 |
| 后台 | 存档 `runtime/games/<gid>.json` 的 `decisions[]`、`/api/advise` 响应的 `decision`、复盘脚本 `experiments/analyze_game.py` |

## 6. 验证记录

* 单元测试：`tests/test_analyze_game.py`（two_phase 专属）+ `tests/test_explain_and_multi.py`（7 策略通用）。
* **行为不变性**：插桩后对 200 局重新跑基准，5 个策略的平均轮次与插桩前**逐位一致**
  （6.125 / 6.260 / 6.550 / 6.775 / 7.045）；`explain=True` 的额外耗时约 +2%（粒子）～ +59%（两阶段，
  绝对值 1ms/局 → 1.5ms/局）。
* 浏览器实测：逐步猜测页提交一轮后回看第 1 轮理由、撤销后理由回到待反馈状态、
  多策略卡片 3 张各自带 10 条理由、手动模式交给策略后槽位被填满且理由同步展示。

## 7. 已知取舍

* 理由文本是为**人类阅读**写的（含中文变量名与准则名），不作为机器决策依据；
  机器可读的字段是 `candidates[].size / chosen / inCandidateSet` 与 `note_extra` 里的数值。
* 目前只有 `two_phase` 有“阶段”概念，因此 `phase` 字段对其它策略是 `null`；
  前端会跳过阶段行，不影响展示。
